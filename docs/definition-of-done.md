## 1. 通用 DoD 十条

一个任务"完成"当且仅当以下十条全部成立，证据=PR 内按 §3 模板填写的验证记录：

1. **追溯**：PR 描述逐条引用任务卡"对应章节"的设计条目，并用一句话复述预期行为（可观察结果，非"实现 XX 功能"）。
2. **三场景**：验收标准的正常/边界/失败三行各有对应自动化测试或人工验证记录；任一场景缺失不得合并。
3. **测试落地**：任务卡"自动化测试清单"所列用例全部存在于代码库（文件+用例名），允许等价改名但 PR 中列新旧映射；不允许"写了测试"却指认不到用例。
4. **检查项通过**：§4 基线 + 任务卡注明的例外项；实际输出（尾部摘要行）贴入 PR。
5. **评审通过**：标准 PR 评审通过；⚠ 任务另按 §5 完成独立评审与人工复核点。
6. **同步四查**：API 契约 / 数据库迁移 / 配置 / 文档四项逐项声明结果；**"无需变更"必须显式写明**，需要变更的同步在同一 PR 内完成（api-design.md 升版、.env.example 增行、README/runbook 更新等）。
7. **白名单纪律**：PR 变更文件 ⊆ 任务卡"修改范围"；白名单外文件出现即打回（跨任务改动=先改任务卡并升版本文档）。
8. **证据留痕**：验证记录只填**实际执行过**的项；未执行的检查不得勾选、不得写"应通过"；证据形式=命令输出摘要 / CI run 链接 / 截图，随 PR 永久可查。
9. **断言完整性**：禁止删除或弱化已有断言来让测试通过；确因需求变更需要修改断言，必须在 PR 中单独一节说明理由并经评审批准（反模式 #4）。
10. **提交粒度**：PR 内每个提交语义单一；"顺手"修复、格式化无关文件、重构相邻代码均不允许。

## 2. 反模式黑名单（六条，逐条对应处理）

| # | 反模式 | 强制规则 |
|---|---|---|
| 1 | 仅凭"页面能打开"判完成 | 验收必须含内容断言：关键元素/数据/文案在响应中（DoD 2、task-breakdown §1.5） |
| 2 | 仅凭 HTTP 200 判 API 正确 | 每契约断言三件套：状态码 + 响应体关键内容 + 适用头（noindex/安全头/重定向目标） |
| 3 | 只测正常输入 | 三场景强制；拒绝路径必须断言状态码与错误体（DoD 2、§5-I） |
| 4 | 删断言凑通过 | DoD 9：删/改断言须单独说明+评审批准 |
| 5 | 多个无关功能一个提交 | DoD 7/10：白名单+单语义提交，违规打回 |
| 6 | 完成后无证据 | DoD 8：验证记录是完成判定的唯一依据 |

## 3. PR 验证记录模板（PR 描述必填段，执行时逐项勾选）

```markdown
## 验证记录（仅勾选实际执行项；未执行不得勾选）
- 场景覆盖：正常 [用例名] / 边界 [用例名] / 失败 [用例名]
- 自动化：ruff check（尾行：____）、ruff format --check（____）、pytest <目标>（____ passed）
- 例外检查项（按任务卡）：[如 makemigrations --check / check --deploy，附输出]
- 人工验证（无自动化覆盖项）：[操作步骤+结果/截图/录屏]
- 同步四查：API：__ / 迁移：__ / 配置：__ / 文档：__
- 断言变更说明（如有）：[理由]
- 评审：标准评审 @__ / 独立评审（⚠卡）@__ / 人工复核点：[结论]
```

## 4. 检查项基线

- **格式检查**：`ruff format --check`（每任务必过）。
- **静态检查**：`ruff check`（每任务必过）。
- **测试**：`pytest <任务卡指定目标>`（每任务必过；用例清单见卡）。
- **迁移例外**：产出或触及迁移的任务加 `makemigrations --check`（T-005、T-007、T-008、T-010、T-012、T-035）。
- **部署链路例外**：加 `manage.py check --deploy`（prod settings）（T-031、T-033、T-035、T-041）。
- **类型检查：V1 不适用**——依据为已批准决策（`technology-decisions.md` 决策修正 #3：mypy + django-stubs 后置到上线稳定后独立 PR 引入；见 `development-plan.md` §3 可选增强区）。此为**显式不适用声明，不是遗漏**；引入时按可选增强流程评审。
- **前端 JS**：V1 量极小，无独立 lint/类型检查，靠评审 + L3 旅程覆盖（TST-1/ADR-02 已声明边界）。

## 5. 高风险加严模板（⚠ 任务按类别适用；均含"独立评审 + 指定人工复核点"）

**M 迁移类**（T-005、T-007、T-008、T-010、T-035）
1. 迁移文件正向人工评审：字段/索引/约束逐项对照 database-design 数据字典，评审记录留 PR。
2. 从零建库自动回归（pytest 建库即跑全迁移，隐式）+ `makemigrations --check` 通过。
3. **禁止修改已合并进 main 的迁移**；需要变更=追加新迁移。
4. 破坏性变更跨版本执行（OPS-2/DM-12 三步法），PR 中声明兼容策略。
5. 人工复核点：迁移 SQL 摘要（sqlmigrate 输出）贴 PR。

**A 认证类**（T-002、T-027、T-041）
1. 失败场景全覆盖：错误凭证、连续失败锁定、锁定期间正确密码拒绝、改密后旧密码失效。
2. 配置逐行对照 security-design §1/§2 表人工复核，复核记录留 PR。
3. 错误信息通用化（不泄漏账号存在性，EX-02）。
4. 人工复核点：settings 中认证/会话相关每一项与设计值一致。

**I 输入处理类**（T-006、T-011、T-013、T-017、T-025）
1. 攻击语料集必测：XSS（script/onerror/javascript:/data:/iframe/style）、SQL 注入 payload、伪装扩展名文件、超限文件；全部"拒绝或净化"断言。
2. 拒绝路径断言状态码 + 错误体内容（不得 200 包错误，api §3）。
3. 白名单/净化/校验规则的任何放宽都需单独评审（security §4）。
4. 人工复核点：语料清单与 security §4/§5 验收行逐条对应。

**P 权限类**（T-014、T-018、T-026、T-027、T-028）
1. 每个受保护端点三路径必测：未登录 / 已登录非授权（本系统即非 staff）/ 缺 CSRF。
2. 草稿可达性逐路径复核：七处消费点（列表/详情/搜索/归档/上下篇/项目关联/sitemap）逐一有断言（AD-6）。
3. 人工复核点：路由表遍历核对——公开 urls 无任何草稿可达路由；受保护路由均在 /admin/ 前缀下。

**D 生产部署类**（T-033～T-037、T-041）
1. 部署前快照证据（文件名+时间戳，OPS-3）。
2. 部署后只读冒烟四 URL 全 200：/healthz、/、/articles/、/sitemap.xml。
3. 回滚路径每个首次执行任务实测一次（重部署上一 tag）。
4. 人工复核清单：安全组仅 80（后台隧道/白名单）、非 root 运行、镜像/仓库无密钥、备份目录权限 600。
5. 中止条件：冒烟任一失败=立即回滚上一 tag，问题立卡新任务，不得带病迭代。

## 6. 失败处理协议

| 级别 | 处理 | 恢复 | 对其他任务影响 |
|---|---|---|---|
| 分支级（实现/测试失败） | 丢弃分支或追加修复提交，PR 不合并即无影响 | 重做或任务卡升版（连续两次评审不过→讨论拆分） | 下游任务保持"阻塞中"直至依赖合并 |
| 迁移级 | PR 内迁移可自由重做（未进 main） | 见 §5-M；已部署生产的按 OPS-2 向后兼容处理，极端用部署前快照恢复 | 阻塞一切依赖该表的模型/视图任务 |
| CI 级 | 红=修复或还原 | 禁止 force-push 绕过；main 恒绿是硬约束 | CI 红期间冻结合并，不影响本地开发 |
| 部署级（D 类） | 冒烟不过=立即回滚上一 tag | 数据异常→停写入→快照恢复（runbook 流程） | 部署回滚不影响已合并功能；验收 T-039 顺延 |

## 7. 全局禁改清单（任何任务不得触碰）

`.env` 实体与一切密钥/凭证文件；**已合并进 main 的迁移文件**；`db.sqlite3` 与 `media/` 内容；GitHub Secrets 与服务器系统配置（走 runbook 流程变更）；其他任务白名单内的文件（跨任务改动=先改任务卡升版）；与项目无关的工具目录。
